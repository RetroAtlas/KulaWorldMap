# CLAUDE.md

Guidance for AI agents working in this repo. Read [README.md](README.md) first: what this is, what the disc stores, how to rebuild it. This file is rules. The readings of the disc and the evidence for each are in [docs/](docs/), and the argument for a reading is in the commit that landed it, so a new finding goes to those two places and not here.

## Before touching the parser, the viewer's axes or the artwork

Read [docs/level-format.md](docs/level-format.md) before changing anything under `tools/` that reads a level, or anything in the viewer that turns a cell into a point on the screen. Four readings in it cost more than the rest to get right, and none can be settled from the disc alone, since a mirror image or a shifted framing reads as cleanly as the truth and a kind is named by what the game shows:

- The lattice is 34 x 34 x 34, indexed `x*1156 + y*34 + z`. `z` counts downward, so the smallest `z` in a level is its highest block, and seen from above with `x` to the right, `y` counts down the page.
- The cell closes a record; it does not open the next one. The build's cross-check passes under both framings, so it cannot tell them apart.
- The six slots of a record are the six faces of its block, in the order top, `+x`, `+y`, `-y`, `-x`, underside. A slot has no position of its own: 51 records are zeroed past the first slot, and a range test on slots once read 255 objects out of them.
- The five lattice styles and a record's kind word are one enumeration of block kinds; what stands on a block is named by its type alone.

Keep the cross-check in `tools/kula_build.py` fatal, and keep `tools/kula_score.py --guide` passing when a name or a points value changes: those two hold the readings and the names to the disc. Do not re-derive the lattice from file sizes.

Read [docs/tgi.md](docs/tgi.md) before touching `tools/kula_tgi.py`, `tools/kula_tex.py` or `tools/kula_skins.py`, or anything in the viewer that picks a texture for a face, and [docs/ggi.md](docs/ggi.md) before touching `tools/kula_ggi.py`.

## Conventions

- [`backlog/`](backlog/) holds the open questions, one file per question, with what has been ruled out. Read it before starting anything large. A question earns a file when the gap between finding it and answering it is long enough for the reasoning to be forgotten; the commit that answers it deletes the file and says what was decided.
- The deployed site is `public/`, and the host serves that directory, so repo artefacts (`README.md`, this file) cannot ship by accident. `.github/workflows/static.yml` is the same workflow as the other RetroAtlas maps, action versions included.
- Dependency-free ES modules, no build step, no framework. The page must work when opened from a plain static server.
- `public/map_data.json` and `public/objects.json` are generated by `tools/kula_build.py` and committed. Never hand-edit them; change the tool and rebuild.
- `public/annotations.json` is the opposite: hand-curated, never generated. It is where names for the game's numbered kinds and types go, and the viewer treats a missing name as normal rather than as an error. A type whose one varying field is a colour or a tier names each value under `variants` with `by` saying which field; one whose field is a direction says so with `facing`; one a switch turns on and off says which field holds whether it starts on with `state`; and `points`, with a level's `score` where the disc holds more than can be collected, are the two things curated there that are not names, because the disc holds neither. Every entry's note says what the name rests on, and a name that rests on a guess does not go in.
- Images are compressed on the way out, never in a follow-up commit: `tools/png.py` writes RGB wherever the alpha says nothing and runs `oxipng` over what it wrote, and `tools/ogcard.js` does the same to the card it renders. Without `oxipng` on PATH the build still produces a correct file, only a larger one, so do not commit one built that way.
- The disc is never committed, and `.gitignore` keeps `*.bin` and `*.cue` out.
- `?survey` on the viewer opens the notebook behind the map: click a block to write down what the game really shows on it, then copy or download the marks. A mark is keyed to the lattice cell and a face and nothing else, never to a record, which is what lets a decode be scored against it rather than confirmed by it. Marks live in `localStorage` until exported, and the deployed page keeps the panel hidden without the flag.

## Naming

A level is titled by the number the game's pause screen gives it, which the build ships as `shown` wherever the engine computes one, and where the disc's own name differs the viewer says so beside the title. **The pack path plus the index inside it is the key**, since a name is not unique. World ids are the disc's directory names, which is all the game has; a friendlier name is a curated override in `annotations.json` under `worlds`, with a source outside the disc, and the viewer falls back to the id rather than inventing one.

## Code comments

Default to none, comment only where the code is genuinely hard to follow, and never reference the history of the code. A comment must not need editing when a constant is tuned or a kind is added, so do not enumerate kinds or restate values in prose.
